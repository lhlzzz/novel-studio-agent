## 主题

`CloakHQ/CloakBrowser` 接入方式评估，用于修复当前 `xiaoping` 项目中的网页检索能力。

## 资料来源

- GitHub 仓库：`CloakHQ/CloakBrowser`
- 已读取：`README.md`、`pyproject.toml`、`examples/basic.py`、`examples/persistent_context.py`、`Dockerfile`

## 已确认事实

### 1. 它的定位不是独立 MCP，而是浏览器执行层

- README 明确把它描述为 `Drop-in Playwright/Puppeteer replacement`。
- Python 用法是把原先 `playwright` 启动逻辑替换成 `from cloakbrowser import launch`。
- 这说明它最适合替换“浏览器启动器”，而不是直接替换 Codex 当前内置的 MCP 协议本身。

### 2. Python 接入门槛低

- `pyproject.toml` 显示它依赖 `playwright>=1.40`、`httpx>=0.24`。
- README 安装方式是 `pip install cloakbrowser`。
- 示例 `examples/basic.py` 说明最小调用是：
  - `from cloakbrowser import launch`
  - `browser = launch(headless=False)`
  - `page = browser.new_page()`
  - `page.goto(...)`

### 3. 支持持久化 profile

- `examples/persistent_context.py` 使用 `launch_persistent_context(PROFILE_DIR, headless=False)`。
- 这意味着如果后续需要长期会话、Cookie、资料页连续验证，可以给 `xiaoping` 单独维护浏览器 profile 目录。
- 但这不等于允许登录真实账号；真实账号操作仍然受 老板批准约束。

### 4. 它支持 Docker 方式运行

- `Dockerfile` 里已经包含 Chromium 依赖、Node.js、Python wrapper、binary 预下载。
- README 提供：`docker run --rm cloakhq/cloakbrowser cloaktest`
- 这说明它有两种部署路径：
  - 本机 Python 包方式
  - Docker 容器方式

### 5. 首次运行需要下载浏览器二进制

- README 说明首次运行会自动下载约 `200MB` 的 stealth Chromium binary。
- 在当前 `network restricted` 环境下，这一步不能由我直接完成。

## 与当前工作流的适配判断

### 适配点

- 目前 `Playwright MCP` 失败现象是“浏览器实例占用”。
- `CloakBrowser` 可作为新的、独立的浏览器启动层，绕开当前被占用的 Playwright 浏览器实例。
- 对 `xiaoping` 来说，它适合执行“公开网页检索、页面读取、资料抓取、截图留证”这一类动作。

### 不适配点

- 它不能直接让 Codex 内置的 `mcp__playwright__*` 工具自动切换过去。
- 也就是说，装上 `CloakBrowser` 之后，我不能立刻继续使用现有 MCP 按钮式工具链，除非外层再包一层新的调用方式。
- 如果目标是“让 Codex 继续像现在一样点网页”，还需要额外桥接层。

## 最小可用接入方案

### 方案 A：把它当独立 Python 抓取器使用

适用目标：尽快恢复 `xiaoping` 的网页研究能力。

做法：

1. 在可联网环境安装 `cloakbrowser`。
2. 新建一个项目内脚本，例如：`workspaces/xiaoping/tools/cloak_research.py`。
3. 这个脚本负责：
   - 启动 `CloakBrowser`
   - 打开目标网页
   - 读取标题、正文、链接、可见文本
   - 必要时截图到 `workspaces/xiaoping/evidence/`
   - 把结果整理进 `RESEARCH.md`

优点：

- 最快落地。
- 不依赖修改 Codex 内置 MCP。
- 对“蓝 V 最佳变现路径”的公开检索已经够用。

缺点：

- 不是交互式浏览器 MCP。
- 需要额外写脚本与本地运行入口。

### 方案 B：把它做成新的浏览器服务层

适用目标：后续长期替代当前不稳定的浏览器执行环境。

做法：

1. 用 Docker 或本机方式启动 `CloakBrowser`。
2. 在外层再做一个本地服务或适配器。
3. 让这个适配器暴露出“打开页面、点击、抓文本、截图”的统一接口。
4. 再考虑与现有 Codex/Claude 工作流对接。

优点：

- 长期更稳定。
- 后续多个项目都能复用。

缺点：

- 明显超出 `xiaoping` 当前“先解决网页检索”的最小需求。
- 需要更多工程时间。

## 对当前 xiaoping 的结论

如果目标只是尽快回答“蓝 V 最好的变现路径”，最合理的是：

- 不去重构整个浏览器基础设施。
- 直接采用 **方案 A**，把 `CloakBrowser` 当独立研究脚本的浏览器内核。

这样可以先恢复：

- 搜公开视频号/公众号/微信生态相关文章
- 读取蓝 V 官方说明与功能边界
- 对公开案例页面做内容提取
- 给 `xiaoping` 输出有网页依据的变现路径判断

## 当前阻塞

- 当前环境是 `network restricted`，我不能直接安装 `cloakbrowser` 或下载其 Chromium binary。
- 当前没有现成的 `CloakBrowser` 本地安装结果，也没有为 Codex 配套的适配脚本。
- GitHub `search_code` 在本环境认证失败，因此未继续做更深的仓库代码级搜索。

   - 列出安装与运行命令
3. 如果你想做长期方案，再单独规划一个浏览器适配层，而不是挤在 `xiaoping` 本轮任务里一起做。

ComfyUI + Wan2.1 本地生成能力，以及 Pixelle-Video / MoneyPrinterTurbo / MediaCrawler 对 xiaoping 视频制作链路的价值。

## ComfyUI + Wan2.1 检查结论

### 已具备

- ComfyUI wrapper 可运行：`/root/hermes/company-ai-system/tools/external/bin/comfyui --help`。
- ComfyUI quick test 可通过，版本为 `ComfyUI 0.22.0`。
- ComfyUI 当前源码已经内置 Wan 相关节点和模板：`comfy_extras/nodes_wan.py`、`comfy_api_nodes/nodes_wan.py`、`blueprints/Text to Video (Wan 2.2).json`、多个 Wan2.1/2.2 workflow templates。
- 模板中存在本地 Wan2.1 text-to-video 工作流，可引用 `Comfy-Org/Wan_2.1_ComfyUI_repackaged`。

### 尚不具备

- 本地模型目录基本为空：`tools/external/repos/ComfyUI/models` 总量约 156K，没有 Wan2.1 权重。
- 当前环境没有可用 GPU：`nvidia-smi` 不存在；ComfyUI quick test 显示 CUDA unavailable，只能 CPU。
- 本地 Wan2.1 T2V 1.3B 模板至少缺：
  - `models/text_encoders/umt5_xxl_fp8_e4m3fn_scaled.safetensors`
  - `models/vae/wan_2.1_vae.safetensors`
  - `models/diffusion_models/wan2.1_t2v_1.3B_fp16.safetensors`
- 14B 模板还会额外缺 `wan2.1_t2v_14B_fp8_scaled.safetensors`、alpha VAE、LoRA 等更重权重。
- ComfyUI Wan API 节点是云 API 节点，隐藏输入包含 Comfy org auth token/API key，并标价；这不是本地免费生成。

### 判断

当前不能“直接本地生成 Wan2.1 视频”。

原因不是 ComfyUI 本体缺失，而是：缺 Wan2.1 模型权重 + 当前没有 GPU。即使下载 1.3B 权重，在当前 CPU 环境也很可能非常慢，不适合作为稳定生产链路。

## 三个仓库的价值判断

### Pixelle-Video

仓库：`https://github.com/AIDC-AI/Pixelle-Video`

- 定位：AI 全自动短视频引擎。
- README 明确支持：输入主题后自动写文案、生成 AI 配图/视频、合成语音、加 BGM、一键合成视频。
- 明确提到支持 AI 视频生成模型如 WAN 2.1，以及 ComfyUI API Key、RunningHub 48G 显存机器调用。
- 对 xiaoping 价值：高。更像完整生产线，可作为“ComfyUI/Wan2.1 + TTS + BGM + 合成”的主候选。
- 注意：本地部署仍需模型/API/显存或云端服务；不能默认免费直接跑。

### MoneyPrinterTurbo

仓库：`https://github.com/harry0703/MoneyPrinterTurbo`

- 定位：一键生成高清短视频。
- README 明确支持：文案生成、素材、字幕、BGM、TTS、9:16/16:9、多模型接入、本地素材。
- GPU 非必需，主要依赖云端 LLM/TTS/在线素材时 CPU 也能跑。
- 对 xiaoping 价值：高，尤其适合快速把脚本批量做成“讲解类短视频”。
- 局限：它更偏素材拼接/字幕/TTS/合成自动化，不等同于本地 Wan2.1 视频生成器。

### MediaCrawler

仓库：`https://github.com/NanmiCoder/MediaCrawler`

- 定位：多平台自媒体公开信息/评论采集工具，支持小红书、抖音、快手、B 站、微博、贴吧、知乎等。
- 对 xiaoping 价值：中。不是视频生成工具，但适合做选题验证、评论痛点收集、爆款内容拆解、用户反馈分析。
- 风险：README 明确有免责声明，禁止非法用途和大规模爬虫；使用时必须遵守平台规则、登录态授权和 老板批准。

## 当前建议

1. 短期继续用 Remotion 做确定性内部样片。
2. 中期优先验证 Pixelle-Video，因为它更贴近“自动短视频生产线 + ComfyUI/Wan2.1”。
3. MoneyPrinterTurbo 作为脚本转讲解类视频的备选生产线。

## 关键结论

1. 蓝 V 账号不应优先按“个人副业泛内容”设计，而应优先按“企业可信背书 + 微信生态承接 + 可合规成交”的闭环设计。

3. 最容易先验证的不是重直播带货，而是蓝 V 可信身份能支撑的三类低压路径：
   - 本地/企业服务获客：用短视频讲真实问题和解决流程，承接到合规咨询/到店/表单/客服。
   - 微信小店轻商品/资料包：用视频号内容解释需求，用小店或小程序承接低价标准化产品。
   - 企业可信背书型知识内容：围绕行业避坑、流程清单、案例拆解做内容，但不承诺收益或结果。
4. 私域导流、二维码、私人联系方式、第三方交易、夸大宣传、低价引流等方向有明显平台治理风险，不能把“引流私域”当作默认打法。
5. 如果要进入真实视频号助手/微信小店后台查看蓝 V 权限，需要 老板明确批准；本轮只保留为后续只读核验动作。

## 候选获利路径优先级

1. P0：蓝 V 本地/企业服务获客
   - 优点：蓝 V 身份降低信任成本；不必先追大流量。
   - 内容形态：问题拆解、避坑清单、服务流程、前后对比、常见误区。
   - 承接：客服、表单、服务号、小程序或线下到店；具体路径需以后合规核验。

2. P1：微信小店轻商品/资料包
   - 优点：比高价服务轻，适合先验证需求。
   - 内容形态：清单、模板、工具包说明、案例拆解。
   - 承接：微信小店/小程序商品；定价、上架、收款必须 gate。

3. P2：直播/短视频带货
   - 优点：商业化链路直接。
   - 风险：需要商品、资质、供应链、直播能力和平台规则核验；不适合作为当前第一步。

4. 暂缓：纯私域引流/重咨询成交
   - 原因：治理风险更高，也容易触发报价、私信、收款、对外承诺等 gate 动作。

### 1.4 X 研究结论（可执行）

1. **不要把 X 平台分成当冷启动主利润**——门槛（Premium、500 粉 verified、500 万曝光/3 月）高，且算法/规则可变。  
2. **X 更适合：注意力 + 信任 + 外链成交**（数字产品、咨询线索、newsletter）。  
3. 内容形态上，官方与从业者都偏：**能拉对话的帖/串帖**，不是纯堆图。  
4. 与 xiaoping 推文包对齐：**用 X 串帖讲「小商家效率模板」问题钩子 → 成交位放数字包/闲鱼/Gumroad（均需 gate）**，而不是先冲广告分成。
